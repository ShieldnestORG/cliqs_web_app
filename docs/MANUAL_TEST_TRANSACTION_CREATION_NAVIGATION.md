# Manual Browser Test: Transaction Creation Navigation

> **Cluster:** testing · **Tags:** manual-test, transaction-creation, navigation, sidebar, qa · **Related:** [User Guide](App%20User%20Guide.md), [Transaction Page Redesign PRD](ui/TRANSACTION-PAGE-REDESIGN-PRD.md), [PRD.md](PRD.md)

## Purpose
Manually verify that creating a transaction successfully navigates to the transaction detail page.

## Prerequisites
- Development server running: `npm run dev` (accessible at http://localhost:3003)
- A multisig account exists in the database
- The multisig has an account on-chain with some balance

## Test URL
http://localhost:3003/coreum/core14rmczf6t6qldyrqrv4jd0zzypkuymrhvsxazxf/transaction/new

(Or use any valid multisig address from your database)

## Test Steps

### 1. Navigate to Create Transaction Page
1. Open browser
2. Go to: `http://localhost:3003/coreum/core14rmczf6t6qldyrqrv4jd0zzypkuymrhvsxazxf/transaction/new`
3. **Expected:** Page loads with the browser tab titled "New Transaction - [chain]", a breadcrumb ending in "New Transaction", and the transaction type selector. There is no `<h1>` "New Transaction" on this page — do not fail the step looking for one.

### 2. Fill Out Transaction Form
1. In the transaction type selector, stay on the **"Standard User Commands"** tab and click **"Send"**, listed under the `// Transfers` section heading. (The other tab is "Validator Commands"; the other standard sections are `// Staking & Governance` and `// Advanced`.)
2. Fill in the form fields:
   - **To Address:** Any valid address (e.g., `core1test123456789abcdefghijklmnopqrstuvwxyz`)
   - **Amount:** Any valid amount (e.g., `1`)
   - **Denom:** Should be pre-filled (e.g., `ucore`)
3. **Expected:** Form fields are populated and no validation errors show

### 2a. Verify Gas Auto-Sizing
1. Scroll to the Gas Limit / Gas Price / Memo row below the message form
2. **Expected:**
   - **Gas Limit** is pre-filled to `200000` for a single Send (100,000 flat + 100,000 for MsgSend, from `gasOfTx` in `lib/txMsgHelpers.ts`). It is editable.
   - **Gas Price** shows the chain's value (e.g. `0.0625ucore`) and is **disabled** — it cannot be edited.
   - Adding a second message raises the gas limit by that message's amount, without adding a second 100,000 of overhead.

### 3. Verify Form Validation
1. Check that the "Create Transaction" button becomes enabled when form is valid
2. **Expected:** Button is clickable (not disabled)

### 4. Create Transaction
1. Click "Create Transaction" button
2. **Expected:** 
   - Loading spinner appears briefly
   - Toast notification titled "Transaction created with ID" with the transaction ID as its description

### 5. Verify Navigation
1. **Expected URL Change:**
   - OLD: `/coreum/core14rmczf6t6qldyrqrv4jd0zzypkuymrhvsxazxf/transaction/new`
   - NEW: `/coreum/core14rmczf6t6qldyrqrv4jd0zzypkuymrhvsxazxf/transaction/[TRANSACTION_ID]`
   
2. **Expected Page Content:**
   - Page heading reads "In Progress Transaction"
   - The layout is a two-column flex row on a wide screen: a 380px "Signing Status" card on the left, "Transaction Details" and "Message Details" cards on the right
   - Signing Status shows `0 of [threshold] signatures`
   - Transaction Details shows chain ID, account number, tx sequence, gas and fee
   - Message Details shows the message you filled in

### 6. Verify Transaction ID
1. Copy the transaction ID from the URL
2. **Expected Format (local JSON database only):** `[timestamp]-[randomstring]`
   - Example: `1771182637864-fce6ylz7c`
   - Timestamp: 13 digits
   - Random string: ~9 lowercase alphanumeric characters
   - Separator: single hyphen
   - This format is generated by `lib/localDb.ts`. **Against MongoDB the ID is a 24-character hex ObjectId instead** — that is not a failure.

### 6a. Verify Sidebar Navigation Behaviour
On a desktop-width window (>= 1024px; below that there is no sidebar, only the header):
1. **Expected:** The left rail sits collapsed as a narrow icon strip.
2. Hover the rail. **Expected:** it expands and floats *over* the page — the transaction cards underneath must **not** shift or reflow.
3. Move the pointer away. **Expected:** it collapses again after a short delay.
4. Hover the rail and click a nav item to navigate. **Expected:** after the route change and with the pointer off the rail, the rail collapses. A rail that stays stuck open after a nav click is a regression.
5. Click the panel icon at the top of the rail (the pin). **Expected:** the rail stays expanded, `aria-pressed` becomes `true`, and page content is now pushed beside it rather than covered. Reload the page — the pinned state persists.
6. Unpin, then tab into the rail with the keyboard. **Expected:** it expands on focus and stays open while focus is inside; `Escape` collapses it.

### 7. Check Browser Console
1. Open browser developer tools (F12)
2. Check Console tab
3. **Expected:** 
   - No errors (red messages)
   - Expect a lot of noise: `lib/txMsgHelpers.ts` still emits verbose `🔍 DECIMAL DEBUG:` logs on every transaction parse. These are not failures.
   - Older runs of this test noted warnings about nested `<a>` tags; treat any that still appear as non-critical, but note them.

### 8. Check Network Tab
1. In developer tools, go to Network tab
2. Look for these requests:
   - `POST /api/transaction` - Status 200
   - `GET /_next/data/development/coreum/[address]/transaction/[txId].json` - Status 200
3. **Expected:** Both requests successful with 200 status codes

## Troubleshooting

### Issue: Page doesn't load
- **Check:** Is the dev server running? (`npm run dev`)
- **Check:** Is the URL correct? (port 3003, not 3000)
- **Check:** Does the multisig exist in your database?

### Issue: "Account Not Found" error
- **Solution:** Send some tokens to the multisig address first
- **Alternative:** Use a different multisig that already has tokens
- **Note:** the multisig account itself pays every transaction fee — funding your own signer wallet does nothing for this. Fund the multisig address.

### Issue: Sidebar stays expanded after clicking a nav item
- **Cause to check:** the rail tracks the pointer with **native** `mouseenter`/`mouseleave` listeners because React's synthetic `onMouseLeave` is dropped when a nav click re-renders the tree. If the rail sticks open, that wiring in `components/Sidebar.tsx` is the first place to look.
- **Not a bug:** the rail staying open while keyboard focus is inside it (the guard tests `:focus-visible`), or staying open because it is pinned.

### Issue: Page content shifts when the sidebar expands
- **Expected behaviour:** unpinned, the rail is `fixed` and overlays content while a spacer div holds the collapsed width, so nothing reflows. Pinned, the spacer widens and content is pushed — that shift is intentional.

### Issue: "Create Transaction" button is disabled
- **Check:** All form fields are filled correctly
- **Check:** Gas limit is a positive integer
- **Check:** Browser console for validation errors

### Issue: Navigation doesn't happen
- **Check:** Browser console for JavaScript errors
- **Check:** Network tab to see if API call succeeded
- **Check:** Server terminal logs for error messages

### Issue: Page navigation succeeds but shows error
- **Check:** Transaction ID format in URL
- **Check:** Server logs for database errors
- **Check:** Network response for error details

## Success Criteria

The test is successful when:
1. ✅ Page loads without errors
2. ✅ Form can be filled and submitted
3. ✅ Transaction is created (confirmed by toast message)
4. ✅ URL changes to transaction detail page
5. ✅ Transaction detail page displays correct information
6. ✅ No critical errors in browser console

## Additional Verification

### Check Server Logs
Look for these log entries in your terminal:
```
POST /api/transaction 200 in [XX]ms
Create transaction success: [transaction-id]
✓ Compiled /[chainName]/[address]/transaction/[transactionID] in [XX]ms
```
The route no longer logs the transaction payload — only the ID. If you see the full
signed body in the server log, that is a regression.

### Check Database
Transaction should be stored in the database:
```bash
# If using JSON file database
cat data/local-db.json | jq '.transactions[] | select(.id=="[transaction-id]")'
```

## Notes
- This test focuses specifically on the navigation flow
- Transaction signing and broadcasting are separate flows and not tested here. In particular the broadcast-time behaviours (pre-broadcast fee balance check, insufficient-funds guidance, multi-endpoint verification, DeliverTx-failure handling) are out of scope here — see the [Transaction Page Redesign PRD](ui/TRANSACTION-PAGE-REDESIGN-PRD.md).
- Multiple transaction types can be tested (Send, Delegate, Vote, etc.)
- This page is the **PubKey multisig** form (`OldCreateTxForm`). A contract (CW3) multisig routes to the proposal form instead and the steps above do not apply.
